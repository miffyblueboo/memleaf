# Candidate reconciliation (unreleased)

The two local candidates `a8ebf6f4` (1147 tests) and `584e0409` (1128 tests)
were siblings, not successive complete releases. Both originated from cumulative
content tree `95284720975c9fdc283817c8608020bbebbbdee1`. The later delivery omitted
68 test IDs and the corresponding broader closeout changes; the earlier one
omitted the later 49 update/recovery tests. Neither old package supersedes the
other. Use the new combined candidate, not a stack of those two patches.

## Reconciliation decisions

Keep the broader candidate's lost-control guards, local Vault binding, strict
shared Writer, logical-ID Forget, planner provenance and revision checks. Carry
forward the narrower candidate's selected deadline/source-time handling,
complete-state journal validation, final settlement recheck, structured failure
receipt, pending MCP projection and exact-target history retention protection.

All new explicit updates use one `ExplicitUpdateManager` and the shared
`MemoryWriter.write_frozen_unlocked`. `MemoryUpdateManager` is a compatibility
name for that same implementation, not another writer. New journals have
`version=2` and normally live in `_state/explicit_updates`. The two earlier
unmerged v1 formats are read and validated before resuming their exact frozen
operation. The legacy B reader contains no write, cancellation or replay method.
Current and legacy journals claiming one logical ID simultaneously are a
conflict; no filename/order winner is chosen and neither payload is erased.

`source_time` is optional. A missing source time produces an `observed_at`
record, not a fabricated message/business time. A structured `deadline` selects
an expression or clears it. The older direct `due_date`/`due_text` editing form
remains supported, but cannot coexist with `deadline` in the same patch.

Without `authorized_scopes`, a trusted caller may edit the selected current
record within its existing scopes. A scope move requires an explicit list
covering BOTH existing and requested scopes and a registered destination.
Restoration additionally requires `restore=True` and a current nonempty body.
Type correction remains opt-in via `allow_type_change=True`. Explicit
`validity=retracted` follows the broader candidate's supported contract;
`retract_memory` also remains available.

A stale request cannot erase its recovery payload merely because a newer head
exists. A genuinely new request based on the new protected revision may replace
the stale plan only after the new request validates. NO_CHANGE does not rewrite
history, clocks or the index. UPDATE replay repairs derived state and then checks
that the current head still matches before claiming success.

Retention protects precisely identified explicit-update/retraction targets and
may clean unrelated historical groups. Legacy or partial/unresolved incremental
work still postpones destructive cleanup globally, because its dependencies are
not safely isolated. Incomplete scans and invalid controls do not authorize
cleanup. Query/migration status only inspects retained plans; it never executes
them or calls a model. Both documented pending-code aliases are preserved.

## Existing test adjustments

All test IDs from both candidates are retained. Conflicting provisional API
expectations were resolved explicitly, not hidden by deleting tests:

* Later scope-move and restoration fixtures supply the explicit authorization
  required by the combined contract. The existing scope-denial tests remain.
* `due_date=None` and explicit withdrawal are supported by the broader API and
  its dedicated tests; they are no longer falsely listed as invalid fields in
  the narrower API's negative matrix. Other protected-field rejection remains.
* A stale-request test now checks that its payload is retained, rather than
  requiring deletion of the recovery evidence.
* Retention errors use the existing `RetentionError` abstraction. The failed
  cleanup test still checks that no files are deleted.
* The process-exit fixture intercepts the shared Writer's CURRENT-head write,
  not a removed private write site or the earlier history write.

Thirteen additional integration tests cover both historical formats, prepare
and applied recovery, original operation IDs, duplicate-journal conflicts,
Forget, current-head supersession, authorization, source time and deadline
ambiguity. Historical fixture payloads were generated by executing each exact
old source snapshot in isolated synthetic Vaults; no production data is used.

The complete suite's initial integration run passed all 1196 tests in the union.
The final suite also includes the thirteen integration tests. Exact final
results and candidate/installation hashes belong to the accompanying report.
Neither count is a real-model quality certificate or native-host acceptance.

## Boundaries

No release, production Vault changes or paid model requests occur as part of
this reconciliation. Raw trusted overwrite is still not a CAS/history API.
File locks coordinate supported local writers, not arbitrary external editors
or cross-machine synchronization. The final comparison before replace is not
an OS-level atomic compare-and-swap. Real Hermes/Codex, authorized Flash and the
same-candidate native matrix remain separate final acceptance requirements.
